# Общая база PM-VPN

Производственная схема предусматривает три голосующих узла: FI-1, FI-2 и EE-1.
Портал на каждом узле обращается к текущему лидеру PostgreSQL. Patroni управляет
выбором лидера через etcd, а приложения проверяют доступность записи через
лидера. Порты БД и etcd доступны только в отдельной сети WireGuard
`vpn-cluster`. Все участники используют одну версию PostgreSQL и etcd.
Для подтверждения записи нужна синхронная реплика; для выборов нужны два голоса.

## Порядок ввода

1. Установить выделенный туннель между всеми тремя узлами. Объявить строго
   по одному адресу /32 на участника и проверить связь в обе стороны каждой пары.
2. Запустить три участника etcd и три узла PostgreSQL/Patroni с синхронной
   репликацией на одну реплику. Проверить выбор лидера, готовность обоих
   ведомых и отказ одного участника на пустой базе.
3. Снять согласованные SQLite-снимки FI-1 и FI-2 и сверить назначения,
   организации и пользователей. Проверить `DIVERGED` на резервных узлах.
   Любые несовместимые назначения одного номера разрешить до импорта.
   Ключи и файлы ранее выданных конфигов сохранить.
4. Перенести таблицы и последовательности, проверить количество строк и
   связи. Сохранить `assignments.slot` как уникальный ключ. В приложении
   сериализовать выдачу слота и проверку лимитов одной транзакцией.
   Отключить чётность лишь после перевода всех писателей на общую базу.
5. Проверить загрузку конфигов, применение пиров, новую выдачу и перенос записи
   после остановки каждого узла по одному. Готовность HTTPS сама по себе
   недостаточна для публикации портала в DNS: нужна готовность выдавать конфиги.

До переключения работающие порталы остаются на SQLite. После первой записи
в PostgreSQL возврат к старому SQLite-снимку требует переноса новых записей.
